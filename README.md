# АиКОС — работы по операционным системам

Выполненные задания по дисциплине «Архитектура компьютера и операционные
системы»: ассемблер RISC-V, bash-скрипты, системные вызовы, межпроцессное
взаимодействие и две многопоточные/многопроцессные системы экзамена.

Код сохранён таким, каким был сдан: решения не переписывались ради оформления.

## Состав

Работы разложены по темам — внутри каждой папки лежит исходный код,
а также отчёты (`.docx`), если они были частью сдачи.

| Раздел | Содержимое |
|---|---|
| [asm/](asm/) | ассемблер RISC-V (GAS): `BDZ1`, `BDZ2`, `BDZW1`, `DZ3`, `DZ4`, `DZ5` |
| [shell/](shell/) | bash-скрипты (`DZ7`) |
| [files/](files/) | работа с файлами через системные вызовы (`DZ8`) |
| [processes/](processes/) | разделяемая память (`DZ9`), передача данных сигналами (`DZ10`) |
| [threads/](threads/) | многопоточная задача «производители — сумматоры» (`DZ10Dvoitsov`) |
| [ipc-exam-system/](ipc-exam-system/) | системы экзамена: многопроцессная (`BDZ3`) и многопоточная (`BDZ4`) |

## Технологии

- **Ассемблер RISC-V** в синтаксисе **GAS** (`.include`, `.globl`, `ecall`,
  регистры `a0`–`a7`, `li`/`la`). Это не x86 и не NASM — для сборки нужен
  кросс-компилятор `riscv64-linux-gnu-as` (или `qemu-riscv64` для запуска).
- **C** (POSIX): системные вызовы файлового ввода-вывода, разделяемая память
  (`shm_open`/`mmap`), сигналы, потоки `pthreads`, семафоры.
- **Bash** — стандартные конструкции языка.
- **Makefile** — в версиях `BDZ3` (сборка `make`, очистка `make clean`,
  демонстрация `make demo`).

## Сборка и запуск

### C-работы

Все программы на C проверены компилятором `gcc 15.2`. Флаги — те же, что в
`Makefile` самой работы:

```bash
# пример для DZ9
gcc -std=gnu17 -Wall -Wextra -pthread -lrt processes/DZ9/server.c -o server
gcc -std=gnu17 -Wall -Wextra -pthread -lrt processes/DZ9/client.c  -o client
```

Для `ipc-exam-system/BDZ3` в каждой версии есть `Makefile`:

```bash
cd ipc-exam-system/BDZ3/v9
make          # собирает exam_server_v3, exam_client_v3, exam_monitor_v3
make demo     # запускает демонстрацию (монитор + сервер + 3 клиента)
make clean
```

> **Важно про флаг `-std=gnu17`.** В двух файлах (`BDZ3/v4-6/exam_system_v1.c`
> и `BDZ3/v9/exam_monitor_v3.c`) обработчики сигналов объявлены как
> `void cleanup()` без параметров — устаревший стиль объявления функций.
> В GCC 14 и новее это стало ошибкой при стандарте по умолчанию (GNU23),
> поэтому сборка падает без явного указания стандарта. Со флагом
> `-std=gnu17` (как в прилагаемых `Makefile`) всё собирается. Исходники
> не правились.

### Ассемблер RISC-V

Код рассчитан на RISC-V, собрать его штатным `gcc`/`nasm` на x86 нельзя.
Локально кросс-тулчейна не было, поэтому сборка ASM-работ **не проверялась**
(см. «Известные ограничения»). Сборка выглядит так:

```bash
# пример для DZ3 (нужен riscv64-linux-gnu-as + ld или gcc для RISC-V)
riscv64-linux-gnu-gcc DZ3.asm -o dz3
# или через ассемблер + компоновщик
riscv64-linux-gnu-as DZ3.asm -o dz3.o && riscv64-linux-gnu-ld dz3.o -o dz3
```

### Bash-скрипты

```bash
bash shell/DZ7/if_example.sh
bash shell/DZ7/run_script.sh   # запускает child.sh
```

## Проверено

Проверка выполнена локально (`gcc 15.2`, `bash`):

- **C: 15 из 15** файлов `.c` компилируются и линкуются с флагами
  `-std=gnu17 -Wall -Wextra -pthread -lrt`. С стандартом по умолчанию
  (GNU23) 13 из 15 собираются, 2 падают — см. раздел «Сборка».
- **Bash: 7 из 7** скриптов проходят проверку синтаксиса `bash -n`.
- **Makefile:** `make -n` в всех трёх версиях `BDZ3` отрабатывает корректно
  (правильные команды сборки сервера/клиента/монитора).
- **Ассемблер RISC-V: не проверялся** — кросс-тулчейна в окружении не было.

## Известные ограничения

1. **ASM-код собран под RISC-V, а не под x86.** Для сборки нужен
   кросс-компилятор `riscv64-linux-gnu-*` (или среда вроде Venus/QTSpim).
   В окружении, где готовился репозиторий, такого тулчейна не было,
   поэтому ассемблерные работы не компилировались. Это ограничение
   окружения, а не ошибка исходников.

2. **Два C-файла требуют флага `-std=gnu17`** на GCC 14+ (устаревшее
   объявление `void cleanup()` в обработчиках сигналов). Подробности —
   в разделе «Сборка». Исходники оставлены без изменений.

3. **`processes/DZ9` — разделяемая память, а не сокеты.** Несмотря на
   возможное упоминание «сокетов» в описании задания, в коде используется
   POSIX `shm_open`/`mmap`. Работа размещена в разделе `processes/`,
   потому что это взаимодействие через общую память между процессами.

4. **В `ipc-exam-system/BDZ3` и `BDZ4` сохранены все три версии** (`v4-6`,
   `v7-8`, `v9` и `v4-5`, `v6-7`, `v8`). Это не дубликаты, а поэтапное
   развитие одного решения: `BDZ3` идёт от одной программы к схеме
   «сервер — клиент — монитор», `BDZ4` — от простой поточной модели к
   версии с конфигами и журналом результатов. Оставлены все, чтобы была
   видна эволюция; самой полной считайте последнюю версию.

5. **Файлы `config*.txt` в `BDZ4/v8`** — входные данные для запуска
   (количество студентов), они нужны для воспроизведения, поэтому оставлены.
   Файлы `results*.txt` с результатами моделирования не публикуются —
   они воспроизводятся запуском.
